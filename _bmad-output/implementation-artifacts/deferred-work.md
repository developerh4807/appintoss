## 퍼즐 코어루프 — 리뷰에서 나온 비차단 개선점

`src/game/patternMatch.ts`, `src/hooks/useCurrency.ts`, `src/pages/PuzzlePage.tsx` 리뷰(step-04, 2026-07-18)에서 나왔으나 이번 스토리를 막지 않는 항목들:

- **순수 게임 로직 유닛테스트 부재** — `tilesForStage`/`generateBoard`/`isMatch`는 부작용 없는 순수 함수라 테스트하기 쉬운데 테스트가 없음. 프로젝트에 테스트 러너 자체가 아직 없음(package.json에 test 스크립트 없음). 7일 출시 스코프에서는 의도적으로 제외.
- **타일 버튼 접근성 부재** — 선택/오답 상태가 배경색으로만 전달됨(`aria-pressed`/`aria-label` 없음). 스크린리더 사용자는 상태를 알 수 없음.
- **`App.tsx` 페이지 라우팅이 타입 없는 문자열 리터럴** — `useState<string | null>`로 `"iaa"`/`"puzzle"` 등을 관리, 오타(`"puzzel"`)가 컴파일은 통과하고 런타임에 조용히 아무 동작도 안 함. 이번 변경이 만든 패턴이 아니라 기존 패턴을 그대로 따른 것.
- **localStorage 쓰기 실패가 UI에 드러나지 않음** — quota 초과/프라이빗 브라우징 등으로 `setItem`이 실패하면 콘솔 에러만 남고, 새로고침 시 진행도가 조용히 되돌아감. Toss WebView 환경에서는 발생 가능성이 낮다고 판단해 이번 스코프에서는 보류.

## [플레이테스트 2026-08-11] iOS 실기기 샌드박스 테스트 피드백 5건

개발자H가 iOS 실기기 샌드박스(`intoss://matchingking`)로 처음 실제 플레이한 뒤 준 피드백. 하나씩 순서대로 완성해나갈 예정이라 전부 기록만 해두고, 착수는 각 항목 답변/설계 확정 후 별도 스토리로 진행한다. 제안된 순서: **②(재시도/영속성 모델) → ①(난이도/컨셉) → ③(배너, 독립적으로 아무때나) → ④·⑤(②확정 후 구체화)**.

`[결정 확정 2026-08-11]` 아래 5개 항목의 "착수 전 확정 필요" 미결 사항이 개발자H와의 세션에서 **전부 확정됐다**. 각 섹션의 `[결정]` 블록 참고. 남은 선행 작업은 **①의 frozen 스펙 재협상 1건**(`spec-pattern-match-core-loop.md`의 "뒤집기/암기 메커닉 금지" 조항) — 이것만 처리되면 5개 항목 모두 구현 스토리로 착수 가능하다.

**확정된 착수 순서와 의존성:**

| 순서 | 항목 | 선행 조건 | 상태 |
|---|---|---|---|
| 1 | ③ 배너 숨김 | 없음 (완전 독립) | 바로 착수 가능 |
| 2 | ② 런 리셋 모델 | 없음 | 바로 착수 가능 |
| 3 | ⑤ 아이템 동선 | ② (재화 유지 확정으로 해소) | ② 이후 |
| 4 | ① 난이도 재설계 | **frozen 재협상 필요** | 재협상 후 |
| 5 | ④ 결과 카드+랭킹 | ②의 리더보드 연동 | ② 이후 |

### ① 난이도 재설계 — "기억력 + 반응속도" 컨셉 전환

현재 그리드(6→24타일)·타이머(15→5초) 두 축이 스테이지 ~10~13 이후로 완전히 평평해져 후반이 단조롭다는 피드백. 개발자H는 컨셉 자체를 기억력+반응속도로 좁히고, 초반(3~5스테이지) 이후 난이도를 급격히 올리며, **그리드는 고정**하는 방향을 제안.

⚠️ **frozen 스펙 충돌**: `spec-pattern-match-core-loop.md`에 `frozen-after-approval`로 "모든 타일은 항상 화면에 보여야 한다 — 뒤집기/암기 메커닉 금지(PRD §5, 기억력 게임 유형은 non-goal)"가 명시돼 있음. "기억력" 요소를 실제로 넣으려면(타일 잠깐 노출 후 숨김 등) 이 frozen 결정을 **재협상**해야 착수 가능.
⚠️ **기존 대기 스펙과의 방향 불일치**: `spec-pattern-match-difficulty.md`(ready-for-dev, 미구현)는 그리드 상한을 24→36으로 **키우는** 방향인데, 이번 피드백은 "그리드 고정"이라 정반대. 배지(도형 판별) 축 자체는 그리드 안 키우고도 재활용 가능해 보임.

**[결정 2026-08-11] — 방향 C(하이브리드) 확정.** 초반 3~5스테이지는 타일 상시 노출로 온보딩하고, 그 이후 구간부터 "잠깐 노출 후 숨김"을 도입한다. 개발자H의 "기억력 + 반응속도" 컨셉과 정확히 일치하며, 그리드를 안 키워도 난이도 상한이 사라지는 게 채택 이유. A안(순수 반응속도)은 재협상 없이 바로 착수 가능하다는 장점이 있었으나 컨셉을 포기해야 해서 탈락.

**[결정 2026-08-11] — 대기 스펙은 그리드 확장만 폐기, 배지축은 살림.** `spec-pattern-match-difficulty.md`의 `MAX_TILES` 24→36 상향은 **폐기**(그리드 고정 방침과 정면 충돌). 반면 아이콘 실루엣 그룹핑 + 보조 도형 배지(모양+배지 conjunction match)는 그리드를 안 키우고도 유효한 난이도 축이라 **그대로 재활용**한다. 위쪽 "패턴매칭 난이도 재설계" 섹션의 `MAX_TILES` 24→36 항목도 이 결정으로 무효화된다.

⚠️ **착수 전 남은 선행 작업 — frozen 재협상 1건.** `spec-pattern-match-core-loop.md`의 frozen Boundaries "모든 타일은 항상 화면에 보여야 한다 — 뒤집기/암기 메커닉 금지(PRD §5)"를 하이브리드 노출 모델로 갱신해야 한다. PRD §5의 "기억력 게임 유형은 non-goal" 서술도 함께 재검토 대상 — 컨셉 자체가 바뀌는 사안이라 PRD 수정이 동반될 가능성이 높다. 참고로 이 frozen 섹션은 2026-07-19에 이미 한 차례 재협상된 이력이 있다(매치 조건 확장 건).

**[결정 2026-08-11] — 메커닉은 "순차 숨김(타임어택)".** 스테이지 시작 시엔 모든 타일이 보이고, 시간이 지날수록 타일이 **하나씩 순차적으로** 숨겨진다. 빨리 맞출수록 정보가 많이 남아 쉬워지므로 반응속도가 직접 보상되고, 늦어질수록 기억에 의존하게 돼 기억력이 요구된다 — 두 축이 별도 장치 없이 하나의 메커닉에서 자연스럽게 결합한다. 대안이던 "전부 숨김"(전형적 신경쇠약)은 반응속도 요소가 약해서, "일부만 숨김"은 두 축이 분리돼 보여서 탈락.

**[결정 2026-08-11] — 하이브리드 전환은 스테이지 4부터.** `balance.ts`의 기존 `GRACE_STAGE_LIMIT=3`과 정확히 일치시킨다(1~3 유예구간은 상시 노출로 온보딩, 4부터 순차 숨김 시작). 새 상수를 만들지 않고 기존 상수를 재사용해 난이도 축들이 같은 경계를 공유하게 한다.

**[결정 2026-08-11] — 숨김 상한 비율로 "순수 추측" 구간 방지.** 그리드가 24타일로 고정된 상태에서 순차 숨김이 끝까지 진행되면, 남은 마지막 페어가 둘 다 숨겨져 실력과 무관한 순수 추측만 남는 구간이 생긴다. 이를 막기 위해 **남은 타일의 최대 N%(초안 70%)까지만 숨기고 나머지는 항상 노출을 유지**한다. 항상 단서가 남아 실력으로 풀 수 있고 구현도 단순하다. 대안이던 "오답 시 재노출"은 시간 압박과 교환되는 구제 장치라 밸런스가 복잡해져 보류(추후 아이템으로 검토 가능).

**[결정 2026-08-11] — 숨겨진 타일을 탭하면 선택은 되되 내용은 계속 숨긴다.** 두 장을 다 고른 뒤에야 결과가 공개되는 신경쇠약 방식. "탭하면 공개된 채 유지"는 기억 부담이 낮아 컨셉이 흐려지므로 탈락.

**[결정 2026-08-11] — 숨김 상태는 형태로 표시(접근성 원칙 유지).** 숨겨진 타일은 아이콘 자리에 물음표·빈 테두리 등 **명확한 형태 신호**로 표시하고, 색상만으로 구분하지 않는다. `DESIGN.md`/`EXPERIENCE.md`의 "매칭 판별은 형태로만, 색상 단독 신호 금지" 원칙을 그대로 지키므로 UX 문서 수정은 불필요하다. 배지축(도형 배지)과도 같은 원칙 위에서 결합된다.

**구현 시 남은 밸런스 과제:**
- 순차 숨김의 **속도 커브** — 스테이지가 오를수록 타일이 얼마나 빨리 숨겨지는지(첫 숨김까지의 지연, 숨김 간격)
- 숨김 상한 비율 70%의 실제 수치 튜닝(플레이테스트 필요)
- 그리드 상한이 없어진 만큼, 숨김 속도·배지 종수·오답 페널티·시간 하한 네 축으로 후반 압박이 계속 오르도록 밸런스 재설계

### ② 무료 재시도 — 오락실(런 리셋) 모델로 전환

현재는 `DAILY_FREE_RETRIES=3`(하루 단위 리셋, `useGlobalRetryCap.ts`)이고 스테이지 진행(`useCurrency.ts`의 `stage`)은 실패해도 절대 안 줄어드는 영구 진행형. 개발자H 제안: 기본 무료 재시도 2회 + 광고 시청 1회 = 총 3회, 다 소진되면 **스테이지 1로 리셋**하고 재시도 카운트도 2로 다시 채워지는 오락실식 "컨티뉴" 구조로 전환. 목적은 "기억력·반응속도 최고기록"을 겨루는 랭킹전 지향.

이건 다섯 항목 중 **가장 파급력이 큼** — 진행도 영속성 모델 자체가 바뀌므로 재화(🪙)·인벤토리 리셋 여부, "최고 도달 스테이지" 별도 영구 필드 신설 여부까지 함께 결정해야 함. 앱인토스 네이티브 게임 프로필/리더보드 API(샌드박스에서도 테스트 가능한 몇 안 되는 기능)를 여기서 붙일지도 검토 대상 — 지금 코드는 이 API를 전혀 안 쓰고 있음.

**[결정 2026-08-11] — 런 리셋 시 재화·아이템은 유지, 스테이지만 리셋.** 런을 거듭할수록 🪙가 쌓여 아이템 전략이 생기는 구조를 택했다. 구현상으로도 `useCurrency.ts`에서 `stage`만 1로 되돌리면 되므로 변경 범위가 작다. "매 런 동일 조건"의 순수 실력 경쟁(전부 리셋)은 공정하지만 뽑기·광고 시청 동기가 약해져서 탈락.

**[결정 2026-08-11 → 조사 후 수정] — 최고기록은 localStorage 주력 + 공식 리더보드 제출 병행(하이브리드).**

최초엔 "처음부터 공식 리더보드 API 연동"으로 확정했으나, 착수 전 SDK 조사에서 **공식 API로는 순위를 조회할 수 없다**는 제약이 발견돼 수정한다. 로컬 후퇴가 아니라 **두 API가 하는 일이 달라서 역할을 나누는 것**이다.

**조사 결과 — API는 실재하되 조회가 안 된다 (`@apps-in-toss/web-framework@2.10.4` 기준, 런타임 브리지 바인딩까지 확인):**

| 함수 | 시그니처 | 용도 |
|---|---|---|
| `submitGameCenterLeaderBoardScore` | `({ score: string }) => Promise<{statusCode} \| undefined>` | 점수 제출 ✅ |
| `openGameCenterLeaderboard` | `() => Promise<void>` | 토스 리더보드 **웹뷰를 띄우기만** ❌ |
| `getGameCenterGameProfile` | `() => Promise<{nickname, profileImageUri} \| ...>` | 닉네임·이미지만, **점수/순위 없음** ❌ |

- **순위 조회 API가 없다.** `openGameCenterLeaderboard`는 반환값이 `void`라 내 순위·상위권·참가자 수를 코드로 못 받는다. 문서에 "보안상 사용자 식별자 미포함" 명시.
- **제출은 문자열 스칼라 하나뿐** (`{ score: string }`, 실수 형태 문자열). 메타데이터 필드 없음. **미니앱당 리더보드 1개**라 "기억력"과 "반응속도"를 별도 랭킹으로 못 나눈다 → 하나의 스칼라로 압축 필요.
- **`isSupported()` 패턴이 없다.** 게임센터 3종은 `isSupported()`를 제공하지 않고, 버전 미지원 시 **`undefined` 반환**이 가드 방식이다. 배너(`TossAds.attachBanner.isSupported()`)와 다르므로 반환값 체크로 가드할 것.
- import는 `@apps-in-toss/web-framework`에서 그대로 하면 된다(web-bridge를 re-export).

**선행 절차(블로커):** ① **게임 카테고리 미니앱**이어야 함 ② **콘솔 미니앱 정보 승인**(영업일 1~2일) 전에는 무조건 `LEADERBOARD_NOT_FOUND` ③ 콘솔에서 **정렬 기준·점수 단위 라벨 등록**(코드가 아니라 콘솔에서 정함 — "높을수록 좋음" 설계가 중요한 이유) ④ 사용자 게임 프로필 없으면 `PROFILE_NOT_FOUND` → **플레이 완료 후 제출** 권고.

**테스트 제약:** 샌드박스 지원됨(광고와 달리 이 벽은 없음, 최소 버전 iOS 2025-12-07 / Android 2025-12-16). 단 **localhost(granite dev)에서는 동작하지 않아 QR 실기기 테스트 필수**(커뮤니티 #1793 공식 답변). **테스트 점수는 셀프 삭제 불가** — 토스에 수동 초기화 요청해야 하므로 실서비스 리더보드 오염에 주의.

**확정 구조:**
1. **localStorage가 주력** — `bestStage`(최고 도달 스테이지)를 런 리셋에 영향받지 않는 영구 필드로 저장. 결과 카드의 "내 최고기록·자체 백분위"는 전부 여기서 나온다. 공식 API는 내 점수조차 읽어올 수 없으므로 이게 필수다.
2. **공식 리더보드는 얇은 어댑터로 제출만** — 점수 확정 지점에서 `submitGameCenterLeaderBoardScore({ score: String(score) })`를 try/catch로 감싸고, `undefined`(미지원)·`LEADERBOARD_NOT_FOUND`·`PROFILE_NOT_FOUND`를 **전부 조용히 무시**한다. 실패해도 게임 흐름에 영향 없어야 하고, 콘솔 승인 전에도 개발이 막히지 않는다.
3. **결과 카드에는 "전체 랭킹 보기" 버튼** → `openGameCenterLeaderboard()`. 호출 시 **미니앱이 백그라운드로 전환**되므로 게임 상태를 먼저 저장/일시정지할 것. 게임 진입 직후 호출은 프로필 웹뷰와 겹쳐 금지.

**[확인 2026-08-11] localStorage 영속성 — 앱을 껐다 켜도 유지된다.** 세션 저장소가 아니라 디스크 영속 저장소이고, 이미 `useCurrency.ts`가 재화·스테이지를 이 방식으로 저장해 실기기 플레이테스트에서 진행 유지가 검증됐다. 단 **영구는 아니다**: 토스 앱 삭제·재설치, 앱 데이터/캐시 삭제(Android), iOS WebView 저장소 회수(용량 압박 시), **기기 변경** 시 지워진다. 즉 최고기록이 계정이 아니라 **기기에 묶인다** — 폰을 바꾸면 0부터다. 하이브리드가 이 약점을 정확히 메운다: 공식 리더보드에 제출된 점수는 토스 서버에 남아 로컬이 날아가도 보존된다. 참고로 현재 코드는 localStorage 쓰기 실패를 콘솔 에러로만 처리하고 UI에 안 드러내는데(위 "퍼즐 코어루프 비차단 개선점" 항목), 최고기록이 걸리면 중요도가 올라가므로 ② 착수 시 함께 검토할 것.

**[결정 2026-08-11] — 점수 공식은 도달 스테이지 중심.** 리더보드가 1개뿐이라 기억력·반응속도를 하나의 스칼라로 압축해야 한다. **도달 스테이지 × 1000 + 남은 시간 보너스** 형태를 기본으로 한다. 직관적이고 "몇 단계까지 갔느냐"가 명확해 공유 메시지로도 쓰기 쉽다. **반드시 "높을수록 좋음" 단조증가 정수로 설계할 것** — 반응속도를 ms로 그대로 쓰면 "낮을수록 좋음"이 되는데 콘솔 정렬 기준을 나중에 바꾸기 번거롭다. 정확한 계수는 ①의 난이도 커브 확정 후 튜닝.

**[결정 2026-08-11] — 일일 재시도 상한(`DAILY_FREE_RETRIES`) 제거, 런당 카운트로 완전 대체.** 런마다 무료 2회로 리충되므로 하루 단위 상한은 중복 제약이다. `useGlobalRetryCap.ts`(하루 3회 일일 리셋)를 폐기하고 런 상태 기반 카운터로 이전한다. **단 광고 일일 상한(`useDailyAdCap.ts`, PRD FR-16)은 그대로 유지** — 이건 광고 과다 노출 방지 장치라 성격이 다르다.

**최종 구조:** 무료 재시도 2회 + 광고 시청 1회 = 총 3회 → 소진 시 스테이지 1로 리셋하고 무료 재시도도 2회로 재충전.

- 참고: 과거 PRD FR-7 원안은 "실패 시 광고/무료재시도 최대 2회"였는데, 2026-07-22에 개발자 피드백으로 "하루 3회"로 바뀐 이력이 있음(`balance.ts` 주석 참고) — 이번이 세 번째 방향 전환. `balance.ts`의 `[UPDATED 2026-07-22]` 주석도 함께 갱신할 것.

**구현 시 남은 과제:**
- "최고 도달 스테이지"를 영구 필드로 신설(런 리셋에 영향받지 않음) — 리더보드 제출 값의 원천이 된다.
- 리더보드 제출 지표를 "최고 도달 스테이지"로 할지 반응속도 기반 점수로 할지 확정(④번 결과 카드와 함께 결정).

### ③ 광고 배너 상시 노출 방식 재검토

`GameShell.tsx`가 퍼즐/뽑기 화면 구분 없이 하단 배너를 항상 렌더링 중. 개발자H는 이걸 손봐야 한다고 판단.

⚠️ 이것도 버그가 아니라 `PRD FR-14`("하단 고정 배너 **상시** 노출")로 명시된 의도된 스펙 — 뒤집는 거면 의도적 결정.

제안: 퍼즐(타이머 도는) 화면에서는 숨기고 뽑기/결과 화면에서만 노출 — 수익화 축소를 최소화하면서 몰입은 지키는 절충안. 다섯 항목 중 유일하게 다른 항목과 의존관계 없이 독립적으로 아무 때나 작업 가능.

**[결정 2026-08-11] — 퍼즐 화면만 숨김 확정.** 타이머가 도는 퍼즐 화면에서는 배너를 렌더하지 않고, 뽑기·결과·인벤토리 화면에서는 유지한다. 수익화 축소를 최소화하면서 코어루프 몰입만 보호하는 절충안.

**[조사 2026-08-11] 토스 공식 스펙 확인 — 배너는 임의 구현이 아니라 공식 수익화 기능.**

- `TossAds.attachBanner(adGroupId, target, options)`는 `@apps-in-toss/web-bridge` 타입 정의(`dist/index.d.ts` L1068)에 실재하는 공식 API. 구버전 `attach`는 `@deprecated`로 표기돼 있고 현재 코드(`useTossBanner.ts`)는 권장 API를 쓰고 있어 그대로 두면 된다.
- 배너·전면(interstitial)·보상형 3종 공식 지원, **실제 정산 있음**: 외부 미디에이션+Toss Ads 운영비 약 30% 공제 후 앱인토스 수수료 15% 추가 공제(2026-03-31까지 수수료 0% 프로모션이었으나 **이미 종료**). 월 수익은 익월 1일 확정·그 달 말일 입금. 정산받으려면 워크스페이스 '정보' 탭에서 정산 정보 등록 후 검토(영업일 2~3일) 필요 — **아직 등록 안 했다면 수익이 발생해도 못 받는다.**
- 문서상 배너는 "체류시간 긴 메인/리스트 화면" 권장, **노출량 최다·eCPM 최저** 포맷. 즉 퍼즐 화면에서 빼는 손실은 노출량 기준으로는 있지만 eCPM 기준 손실은 크지 않다.
- `useTossBanner.ts` L14의 참고문서 URL(`.../광고/BannerAd.html`)은 현재 **404** — 문서가 이동했다. 착수 시 `https://developers-apps-in-toss.toss.im/documentation/common/monetization/iaa/web-banner.md`로 갱신할 것.

⚠️ **정책 조항 검토 — 저촉되지 않는다고 판단.** 공식 문서에 "광고를 의도적으로 숨기거나 다른 UI 요소에 가려 사용자가 광고의 존재를 명확히 인지하기 어렵게 만드는 행위" 금지 조항이 있어 문자 그대로면 이번 결정이 걸려 보인다. 하지만 이 조항은 *같은 화면 안에서* opacity·레이어링으로 광고를 시각적으로 은폐하는 행위(노출 카운트는 먹으면서 사용자는 못 보게 하는 부정 트래픽)를 겨냥한 것이고, 같은 문서가 **화면 전환 시 unmount·`destroy()` 하는 per-screen attach/destroy 패턴을 명시적으로 권장**한다(`return () => { attached?.destroy(); }`). 퍼즐 화면에 배너를 아예 mount하지 않는 것은 은폐가 아니라 문서가 권장하는 라이프사이클 그 자체다. 추가로 "광고는 고객의 서비스 목표를 방해하지 않아야 한다", "인터랙티브 요소 옆에 붙여 오클릭 유발 금지" 조항은 오히려 타이머 도는 퍼즐 그리드 옆 배너를 빼는 쪽을 지지한다.

⚠️ **구현 시 필수 준수 — 주기적 Refresh 금지.** "광고 영역을 주기적으로 Refresh 처리"는 트래픽 조작으로 명시 금지돼 있다. 퍼즐↔뽑기를 빠르게 오갈 때 attach/destroy가 반복되면 사실상 refresh처럼 보일 수 있으므로 **화면 전환 기반 mount/unmount만** 사용하고, 타이머·인터벌 기반 재attach는 절대 넣지 않는다. (SDK 자체 auto-refresh는 렌더 10초 경과 + hidden→visible 전환 시에만 동작.)

**PRD 반영 필요:** 이 결정은 `PRD FR-14`("하단 고정 배너 **상시** 노출")를 뒤집으므로, 착수 시 FR-14 서술을 "퍼즐 외 화면 상시 노출"로 갱신할 것.

재시도 소진 후 이어하기 광고(`PuzzlePage.tsx`의 `handleContinueAd`, PRD FR-17)는 이미 코드에 있음 — 샌드박스 앱이 인앱광고 자체를 지원하지 않아 버튼이 계속 비활성으로 보였을 뿐, 실제 동작 확인은 콘솔 QR 테스트 필요.

### ④ 게임오버 결과 카드 + 랭킹 공유

게임오버 시 현재 랭킹/반응속도 결과를 보여주고 공유를 유도하는 장치 필요하다는 피드백. 완전 신규가 아니라 위쪽 "결과 카드 + 공유 + 초대 보상 (PRD FR-18~20)" 섹션의 **FR-18(동물 티어 결과 카드)이 이미 계획됐다가 미구현 상태로 남아있던 것** — "랭킹" 요소만 새로 얹으면 됨.

②번에서 "최고기록"이 뭘로 정의되는지(도달 스테이지? 반응속도? 리더보드 API 연동 여부?) 먼저 정해져야 카드에 무엇을 보여줄지 확정 가능 — ②번 후행 작업.

**[결정 2026-08-11 → 조사 후 수정] — ②의 하이브리드 확정으로 선행 조건 해소. 단 "랭킹 표시"는 불가능하다.**

최초엔 "랭킹(리더보드 API에서 조회)"을 카드에 넣기로 했으나, ②의 SDK 조사에서 **공식 API에 순위 조회 수단이 없음**이 확인됐다(`openGameCenterLeaderboard`는 `Promise<void>`, 웹뷰를 띄우기만 함). 따라서 카드에 실제 순위(내 등수·상위 N%)를 공식 데이터로 표시할 수 없다.

**결과 카드 구성(수정 확정):**
- 이번 런 도달 스테이지 + 점수(도달 스테이지×1000 + 시간 보너스)
- **로컬** 최고기록과의 비교("최고기록 갱신!" / "지난 최고 12,340점") — localStorage 기반
- 자체 백분위를 넣고 싶다면 **직접 계산한 추정치**여야 하며, 공식 랭킹으로 오인되지 않게 표기할 것
- **"전체 랭킹 보기" 버튼** → `openGameCenterLeaderboard()`로 토스 웹뷰 이동. 이게 순위를 보여주는 유일한 경로다. **호출 시 미니앱이 백그라운드로 전환되므로 게임 상태를 먼저 저장/일시정지**할 것.

FR-18의 "동물 티어" 표현을 유지할지는 카드 디자인 단계에서 확정 — 티어를 남긴다면 도달 스테이지를 티어로 매핑하는 방식이 자연스럽고, 순위를 못 보여주는 만큼 티어가 오히려 성취감 표현을 대신할 수 있다. 공유(FR-19)는 기존 계획대로 기본 공유 시트·항상 노출·무보상.

### ⑤ 아이템 사용 규칙 정비 + 재화 밸런스

전략적으로 플레이할 수 있게 스테이지 클리어 후 뽑기 → 다음 스테이지 시작 전 미리 아이템을 쓰도록 유도하자는 피드백. "스테이지 사이 미리 쓰기" 동선은 `GachaPage.tsx` 인벤토리 탭에 **이미 존재**함(뽑고 나서 "다음 스테이지 시작하기" 누르기 전에 쓸 수 있음) — 문제는 헤더 🎒 버튼으로 **퍼즐 타이머 도중에도 즉시 사용**이 동시에 허용돼 있어 전략 구상이 흐려진다는 점. 즉시사용 버튼을 없애고 뽑기 화면 경유만 남길지가 핵심 결정.

재화 획득 속도(`CLEAR_REWARD=10`, `PULL_COST=3` → 클리어 3회당 뽑기 1회)는 ②번에서 재화가 런마다 리셋되는지에 따라 튜닝 방향이 완전히 달라지므로 ②번 후행 작업.

**[결정 2026-08-11] — 헤더 🎒 즉시사용 버튼 제거, 뽑기 화면 경유만 남김.** 퍼즐 타이머 도중 즉시 사용을 막아 "스테이지 시작 전에 미리 장착"하는 전략 구상 동선을 강제한다. `GachaPage.tsx` 인벤토리 탭의 기존 동선("다음 스테이지 시작하기" 누르기 전 사용)이 유일한 사용 지점이 된다.

**[결정 2026-08-11] — 재화 밸런스 튜닝 방향 확정(②의 재화 유지 결정에 따름).** ②에서 재화가 런마다 리셋되지 **않고 누적**되는 것으로 확정됐으므로, 런을 반복할수록 🪙가 단조 증가한다. 즉 현재 `CLEAR_REWARD=10` / `PULL_COST=3`을 그대로 두면 후반에 재화가 남아돌아 아이템 희소성이 사라진다 — **획득량을 낮추거나 뽑기 비용을 올리는 방향**으로 튜닝해야 한다. 정확한 수치는 ①의 난이도 커브(런 평균 길이)가 확정된 뒤 함께 잡을 것.
