# Deferred Work

`[정리 2026-07-19]` 아래 항목들은 07-17 구 PRD 기준 FR 번호(가챠=FR-4~6, 광고=FR-7~9, 공유=FR-10)로 작성돼 있었고, "동물 캐릭터 가챠/도감" 항목은 07-18 PRD 재작성에서 이미 폐기된 기능(§5 Non-Goal)을 그대로 할 일로 담고 있었다. Implementation Readiness 체크(`implementation-readiness-report-2026-07-19.md`)와 `game-architecture.md`(L113) 양쪽에서 독립적으로 발견된 문제라 현재 PRD(FR-1~20) 기준으로 전면 재작성한다. 실제 구현 대상 기능(재화 뽑기, 광고 배치, 공유)의 의도는 그대로 유효하다 — 번호와 "가챠 대상"만 최신화한다.

## 퍼즐 코어루프 — 리뷰에서 나온 비차단 개선점

`src/game/patternMatch.ts`, `src/hooks/useCurrency.ts`, `src/pages/PuzzlePage.tsx` 리뷰(step-04, 2026-07-18)에서 나왔으나 이번 스토리를 막지 않는 항목들:

- **순수 게임 로직 유닛테스트 부재** — `tilesForStage`/`generateBoard`/`isMatch`는 부작용 없는 순수 함수라 테스트하기 쉬운데 테스트가 없음. 프로젝트에 테스트 러너 자체가 아직 없음(package.json에 test 스크립트 없음). 7일 출시 스코프에서는 의도적으로 제외.
- **타일 버튼 접근성 부재** — 선택/오답 상태가 배경색으로만 전달됨(`aria-pressed`/`aria-label` 없음). 스크린리더 사용자는 상태를 알 수 없음.
- **`App.tsx` 페이지 라우팅이 타입 없는 문자열 리터럴** — `useState<string | null>`로 `"iaa"`/`"puzzle"` 등을 관리, 오타(`"puzzel"`)가 컴파일은 통과하고 런타임에 조용히 아무 동작도 안 함. 이번 변경이 만든 패턴이 아니라 기존 패턴을 그대로 따른 것.
- **localStorage 쓰기 실패가 UI에 드러나지 않음** — quota 초과/프라이빗 브라우징 등으로 `setItem`이 실패하면 콘솔 에러만 남고, 새로고침 시 진행도가 조용히 되돌아감. Toss WebView 환경에서는 발생 가능성이 낮다고 판단해 이번 스코프에서는 보류.

**Source:** step-04 review (blind hunter + edge case hunter), 2026-07-18.

## 패턴매칭 난이도 재설계 — 아이콘 그룹핑 + 보조 도형 배지 + 그리드 상한 확장 (PRD FR-4)

2026-07-19 게임 디자인 세션에서 확정된 난이도 재설계. 그리드 크기·제한시간 두 축만으로는 후반 스테이지가 단조롭거나(같은 종류 압박 반복) 물리적으로 클리어 불가능에 가까워지는 문제가 있어, 아이콘 실루엣 그룹핑(타겟-방해물 유사도)과 보조 도형 배지(모양+배지 conjunction match)를 신규 축으로 추가하고 `MAX_TILES`를 24→36으로 상향하기로 함. `[FIXED 2026-07-19]` 최초엔 배지 대신 색상 변주(hue-rotate)로 검토했으나, 같은 날 Implementation Readiness 체크에서 `DESIGN.md`/`EXPERIENCE.md`의 "매칭 판별은 형태로만, 색상 단독 신호 금지" 원칙과 충돌함이 발견돼 도형 배지로 전환 — UX 문서는 수정하지 않아도 된다(원칙을 깨지 않으므로).

**구현 시 필요한 것**:
- `src/game/patternMatch.ts`: 아이콘을 그룹(개과/고양이과/곰과/기타)으로 분류하는 상수, 배지 도형(●▲■◆ 등) 배정 로직, `isMatch`가 스테이지 구간에 따라 "모양만" 또는 "모양+배지"를 비교하도록 확장, `MAX_TILES` 24→36.
- `src/pages/PuzzlePage.tsx`: 타일 렌더링에 배지 오버레이 추가(색은 보조 신호로만, 배지 모양이 유일한 판별 기준). 컬럼 수는 4 유지(터치 정확도 보호 — 5 이상은 실험 후 결정, 6 이상 금지).
- `spec-pattern-match-core-loop.md`의 frozen 섹션("경로 탐색 로직 없음 — 매칭 조건을 만족하면 매칭 성립")은 이미 2026-07-19에 재협상·갱신 완료 — 이 항목 착수 시 추가 renegotiation 불필요, 다만 실제 코드 구현 시 새 스펙/스토리로 진행할 것.
- 정확한 구간표·배지 종류 수·그룹 구성은 `_bmad-output/planning-artifacts/prds/prd-appintoss-2026-07-17/addendum.md`의 "퍼즐 난이도(그리드 크기 + 아이콘 유사도 + 보조 도형 배지) 밸런스 초안" 섹션 참고.

## [플레이테스트 2026-08-11] iOS 실기기 샌드박스 테스트 피드백 5건

개발자H가 iOS 실기기 샌드박스(`intoss://matchingking`)로 처음 실제 플레이한 뒤 준 피드백. 하나씩 순서대로 완성해나갈 예정이라 전부 기록만 해두고, 착수는 각 항목 답변/설계 확정 후 별도 스토리로 진행한다. 제안된 순서: **②(재시도/영속성 모델) → ①(난이도/컨셉) → ③(배너, 독립적으로 아무때나) → ④·⑤(②확정 후 구체화)**.

### ① 난이도 재설계 — "기억력 + 반응속도" 컨셉 전환

현재 그리드(6→24타일)·타이머(15→5초) 두 축이 스테이지 ~10~13 이후로 완전히 평평해져 후반이 단조롭다는 피드백. 개발자H는 컨셉 자체를 기억력+반응속도로 좁히고, 초반(3~5스테이지) 이후 난이도를 급격히 올리며, **그리드는 고정**하는 방향을 제안.

⚠️ **frozen 스펙 충돌**: `spec-pattern-match-core-loop.md`에 `frozen-after-approval`로 "모든 타일은 항상 화면에 보여야 한다 — 뒤집기/암기 메커닉 금지(PRD §5, 기억력 게임 유형은 non-goal)"가 명시돼 있음. "기억력" 요소를 실제로 넣으려면(타일 잠깐 노출 후 숨김 등) 이 frozen 결정을 **재협상**해야 착수 가능.
⚠️ **기존 대기 스펙과의 방향 불일치**: `spec-pattern-match-difficulty.md`(ready-for-dev, 미구현)는 그리드 상한을 24→36으로 **키우는** 방향인데, 이번 피드백은 "그리드 고정"이라 정반대. 배지(도형 판별) 축 자체는 그리드 안 키우고도 재활용 가능해 보임.

**미결 사항 (착수 전 확정 필요):**
- 순수 반응속도 유지+그리드 고정+배지축(A) / 진짜 기억력 메커닉 도입(B, frozen 재협상 필요) / 하이브리드(C, 초반은 상시노출·후반부터 숨김) 중 방향 선택
- 난이도 커브가 상한 이후에도 계속 오르도록 재설계(그리드 안 키워도 배지 종수·페널티·시간 하한 등으로 압박 지속 가능해야 함)

### ② 무료 재시도 — 오락실(런 리셋) 모델로 전환

현재는 `DAILY_FREE_RETRIES=3`(하루 단위 리셋, `useGlobalRetryCap.ts`)이고 스테이지 진행(`useCurrency.ts`의 `stage`)은 실패해도 절대 안 줄어드는 영구 진행형. 개발자H 제안: 기본 무료 재시도 2회 + 광고 시청 1회 = 총 3회, 다 소진되면 **스테이지 1로 리셋**하고 재시도 카운트도 2로 다시 채워지는 오락실식 "컨티뉴" 구조로 전환. 목적은 "기억력·반응속도 최고기록"을 겨루는 랭킹전 지향.

이건 다섯 항목 중 **가장 파급력이 큼** — 진행도 영속성 모델 자체가 바뀌므로 재화(🪙)·인벤토리 리셋 여부, "최고 도달 스테이지" 별도 영구 필드 신설 여부까지 함께 결정해야 함. 앱인토스 네이티브 게임 프로필/리더보드 API(샌드박스에서도 테스트 가능한 몇 안 되는 기능)를 여기서 붙일지도 검토 대상 — 지금 코드는 이 API를 전혀 안 쓰고 있음.

**미결 사항 (착수 전 확정 필요):**
- 런 리셋 시 재화·인벤토리도 같이 리셋인지, 스테이지만 리셋이고 재화/아이템은 유지인지
- "최고기록"을 앱인토스 공식 리더보드 API로 붙일지, 로컬(localStorage) 개인 최고기록으로 충분할지
- 참고: 과거 PRD FR-7 원안은 "실패 시 광고/무료재시도 최대 2회"였는데, 2026-07-22에 개발자 피드백으로 "하루 3회"로 바뀐 이력이 있음(`balance.ts` 주석 참고) — 이번이 세 번째 방향 전환.

### ③ 광고 배너 상시 노출 방식 재검토

`GameShell.tsx`가 퍼즐/뽑기 화면 구분 없이 하단 배너를 항상 렌더링 중. 개발자H는 이걸 손봐야 한다고 판단.

⚠️ 이것도 버그가 아니라 `PRD FR-14`("하단 고정 배너 **상시** 노출")로 명시된 의도된 스펙 — 뒤집는 거면 의도적 결정.

제안: 퍼즐(타이머 도는) 화면에서는 숨기고 뽑기/결과 화면에서만 노출 — 수익화 축소를 최소화하면서 몰입은 지키는 절충안. 다섯 항목 중 유일하게 다른 항목과 의존관계 없이 독립적으로 아무 때나 작업 가능.

재시도 소진 후 이어하기 광고(`PuzzlePage.tsx`의 `handleContinueAd`, PRD FR-17)는 이미 코드에 있음 — 샌드박스 앱이 인앱광고 자체를 지원하지 않아 버튼이 계속 비활성으로 보였을 뿐, 실제 동작 확인은 콘솔 QR 테스트 필요.

### ④ 게임오버 결과 카드 + 랭킹 공유

게임오버 시 현재 랭킹/반응속도 결과를 보여주고 공유를 유도하는 장치 필요하다는 피드백. 완전 신규가 아니라 위쪽 "결과 카드 + 공유 + 초대 보상 (PRD FR-18~20)" 섹션의 **FR-18(동물 티어 결과 카드)이 이미 계획됐다가 미구현 상태로 남아있던 것** — "랭킹" 요소만 새로 얹으면 됨.

②번에서 "최고기록"이 뭘로 정의되는지(도달 스테이지? 반응속도? 리더보드 API 연동 여부?) 먼저 정해져야 카드에 무엇을 보여줄지 확정 가능 — ②번 후행 작업.

### ⑤ 아이템 사용 규칙 정비 + 재화 밸런스

전략적으로 플레이할 수 있게 스테이지 클리어 후 뽑기 → 다음 스테이지 시작 전 미리 아이템을 쓰도록 유도하자는 피드백. "스테이지 사이 미리 쓰기" 동선은 `GachaPage.tsx` 인벤토리 탭에 **이미 존재**함(뽑고 나서 "다음 스테이지 시작하기" 누르기 전에 쓸 수 있음) — 문제는 헤더 🎒 버튼으로 **퍼즐 타이머 도중에도 즉시 사용**이 동시에 허용돼 있어 전략 구상이 흐려진다는 점. 즉시사용 버튼을 없애고 뽑기 화면 경유만 남길지가 핵심 결정.

재화 획득 속도(`CLEAR_REWARD=10`, `PULL_COST=3` → 클리어 3회당 뽑기 1회)는 ②번에서 재화가 런마다 리셋되는지에 따라 튜닝 방향이 완전히 달라지므로 ②번 후행 작업.

**Source:** 개발자H 실기기 플레이테스트 세션, 2026-08-11. 대화 로그 기준 정리 — 우선순위/미결 사항은 발견 즉시 이 문서에 반영, 답변 확정되는 대로 각 섹션 갱신.
