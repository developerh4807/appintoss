## 3. 지금 코드에 남아 있는 실제 결함

문서 기준으로 코드를 대조하며 확인한 것들이다. **①과 ②는 게임의 주축인 순차 숨김을 직접 무력화한다.**

### ① 미스매치 방패 + 오답 재노출 = 비용 0의 전체 보드 공개 `[심각]`

```
PuzzlePage.tsx:173-178  →  if (shieldCharges > 0) { onConsumeShield(); }
                            else { timer.applyPenalty(3); }
PuzzlePage.tsx:680      →  const isHidden = hiddenIds.includes(...) && !isMatched
                                            && wrongIds.length === 0;
```

방패가 있으면 오답의 **시간 페널티가 사라지는데, 08-13에 추가된 전체 재노출은 그대로 발생한다.** 즉 방패 1개 = **900ms짜리 무료 전체 보드 공개권 1회**다.

방패를 3개 쌓고 스테이지에 들어가 아무 타일이나 두 번 탭하면, 후반 스테이지에서도 아무 대가 없이 보드를 세 번 열어볼 수 있다. **순차 숨김 축 전체가 무력화된다.**

08-13 커밋 주석은 *"판정 기준은 그대로 실제 icon/disguise라 이 공개는 순수 표현(presentation)일 뿐 밸런스에 영향 없다"* 고 적었다. **판정 로직 관점에서는 맞지만 게임 디자인 관점에서는 틀렸다** — 스펙 자신이 이걸 "시간 압박과 교환되는 **구제 장치**"라고 정확히 규정하고 보류했었다. 교환할 시간이 방패로 0이 되면 구제 장치가 아니라 공짜 도구가 된다.

### ② 오답 페널티가 숨김 스케줄을 즉시 전진시킨다 `[심각·미문서화]`

```
useHideSchedule.ts:  const elapsedMs = (stageSeconds - timeLeft) * 1000;
useStageTimer.ts:    applyPenalty = (s) => setTimeLeft(t => max(0, t - s));
```

숨김 경과 시간을 `timeLeft`에서 **역산**하므로, 오답으로 3초가 깎이면 **경과 시간이 3초 순간이동한다.**

스테이지 13 기준 실측:
- `initialSecondsForStage(13)` = 5초, 타일 24장, 숨김 상한 16장
- `graceRatioForStage(13)` = 0.18 → grace 900ms, `intervalMs` = (5000−900)/16 ≈ **256ms**
- 오답 1회 = +3000ms 경과 = **약 11장이 한 프레임에 추가로 숨겨짐**

즉 후반 오답 1회의 실제 비용은 "-3초"가 아니라 **"-3초 + 보드 절반이 즉시 사라짐"**이다. 어느 문서에도 이 결합이 계산된 적이 없다.

**08-11 플레이테스트의 "체감 난이도가 너무 가혹하다"는 피드백의 진짜 원인이 이것일 가능성이 높다.** 08-13의 대응(오답 시 재노출)은 원인이 아니라 증상을 건드렸고, 그 과정에서 ①의 구멍을 만들었다.

### ③ 시간 회복 스택이 난이도를 2축 동시에, 무제한으로 낮춘다 `[중]`

`stageSeconds`는 숨김 스케줄의 **분모**이기도 하다(`graceMs`, `intervalMs` 양쪽). 시간 회복은 "제한시간 +5초"로만 설명되지만 실제로는 숨김 커브 전체를 함께 늘린다.

스테이지 20에서 시간 회복 2개 사용 시:

| | 기본 | +2 스택 |
|---|---|---|
| 제한시간 | 5초 | **15초 (3배)** |
| grace(첫 숨김까지) | 750ms | **2250ms (3배)** |
| 숨김 간격 | 266ms | **797ms (3배)** |

아이템 설명은 `"다음 스테이지 제한시간 +5초"`뿐이고, 스택 **상한이 없다.** 후반 재화가 남아도는 구조(`deferred-work.md` ⑤가 지적)와 결합하면 시간 회복을 5~6개 쌓아 후반 난이도를 사실상 초기화할 수 있다.

### ④ 아이템 3종이 서로 다른 3가지 중복 규칙을 갖는다 `[낮음·UX]`

08-13 변경 결과:

| 아이템 | 중복 시 | 소모 방식 |
|---|---|---|
| 미스매치 방패 | 스택 | 오답 1회당 1개 |
| 시간 회복 | 스택 | **다음 스테이지에 전량 한 번에** |
| 재화 2배 | **금지**(토스트) | 1회 |

각각의 이유는 코드 주석에 타당하게 설명돼 있지만, **유저에게는 세 아이템이 세 가지 다른 규칙으로 동작하는 것으로 보인다.** 화면에 개수가 표시되는 것도 방패뿐이다(`PuzzlePage.tsx:504`).

### ⑤ 콜드 스타트 리셋의 전제가 웹뷰에서 성립하지 않을 수 있다 `[중]`

```
useCurrency.ts:  // loadProgress가 실행된다는 건 예외 없이 "강제종료 또는
                 // OS의 백그라운드 kill 이후 재시작"이라는 뜻이다.
                 return { currency: parsed.currency, stage: 1 };
```

주석은 이 전제를 "예외 없이"라고 단언하지만, 미니앱 웹뷰에서 페이지가 다시 로드되는 경로는 강제종료만이 아니다 — **OS의 메모리 압박에 의한 webview 회수, 토스 앱 내 다른 미니앱 경유 후 복귀** 등도 같은 결과를 낳는다.

문제는 **결과의 비대칭성**이다. 유저가 스테이지 18에 있는데 자기 의사와 무관하게 webview가 회수되면, 재진입 시 **아무 안내 없이 스테이지 1**이다. 오락실 리셋(FR-7)은 "재시도 3회 소진"이라는 납득 가능한 조건이 있는 반면, 이건 조건이 유저에게 보이지 않는다.

최소한 리셋 발생 시 토스트 한 줄("앱이 재시작되어 스테이지 1부터 시작해요")은 필요하고, 이 결정 자체가 **PRD FR-7 런 리셋 모델의 두 번째 트리거**이므로 문서화 대상이다.

## 4. 처음부터 다시 만든다면

우선순위 순이다. 위 세 개가 나머지 전부보다 중요하다.

### ① "플레이 가능한 빌드를 실기기에" 를 1일차 마일스톤으로

지금 순서는 `브리프 → PRD → UX → 아키텍처 → 스펙 → 구현 → 실기기`였고, 실기기가 24일차였다.

바꿀 순서: **`거친 프로토타입 → QR 실기기 → 그 다음에 문서`**

핵심 원칙 한 줄: **"실기기에서 직접 플레이해보기 전에는 어떤 난이도 결정도 frozen하지 않는다."**

07-19 세션과 07-25 스펙(322줄)은 이 원칙만 있었으면 아예 쓰지 않았을 문서다. 08-11에 둘 다 폐기됐다.

### ② 플랫폼 능력 조사(capability spike)를 PRD §4 작성 **전**에

FR을 쓰기 전에 표 하나를 먼저 만든다:

| 하고 싶은 것 | API 존재? | 시그니처 제약 | 승인/콘솔 선행? | 로컬 테스트 가능? |
|---|---|---|---|---|
| 리더보드 순위 표시 | ❌ 조회 API 없음 | — | — | — |
| 리더보드 점수 제출 | ✅ | `{score: string}` 스칼라 1개, 미니앱당 1개 | 승인 1~2일 | ❌ QR 필수 |
| 배너 광고 | ✅ | `attachBanner` | 정산 등록 2~3일 | ❌ |
| 초대 보상 | ✅ | `contactsViral` | 승인 + 리워드 등록 | ❌ |

이 표를 **PRD보다 먼저** 만들었다면:
- FR-8 점수 공식이 처음부터 "단일 스칼라, 높을수록 좋음"으로 설계됐다

- **콘솔 승인 신청이 1일차에 걸렸다** — 리드타임이 코드와 병렬로 소진됐을 것이다

### ③ 리드타임 있는 외부 작업을 1일차에 착수

지금 가장 아픈 지점이다. 게임 카테고리 등록·미니앱 정보 승인(1~2일)·정산 등록(2~3일)은 **코드 완성도와 무관하게 병렬 진행 가능**하다. 26일 동안 한 번도 착수되지 않았고, 지금 시작해도 최소 3~5 영업일이 더 든다.

원칙: **"내가 통제할 수 없는 대기 시간은 프로젝트 첫날에 시작한다."**

### ④ 밸런스 SoT를 처음부터 코드 한 파일로 못박기

08-11 스펙 AD-3의 판단("난이도 파생 SoT는 `balance.ts`")은 정확했다. **1일차에 세웠어야 할 원칙**이다.

- **코드(`balance.ts`, `items.ts`)** = 수치의 유일한 진실. 어떤 문서에도 수치를 복제하지 않는다.
- **문서** = "왜 그 값인가"(설계 의도)와 "어느 방향으로 조정하는가"(조정 신호)만.
- 문서에 표를 그려야 한다면 **코드에서 생성**하거나, 최소한 함수명을 인용해 값 자체는 적지 않는다.

지금은 세 문서에 흩어진 수치 표를 전부 지우고 `balance.ts` 참조로 바꾸는 정리가 필요하다.

### ⑤ frozen 계약을 지킬 수 있는 크기로 줄이기

현재 `spec-pattern-match-difficulty.md`의 frozen 블록은 **60줄**이다. 너무 커서 실제로 다 지켜지지 않았고, 08-13에 두 건이 조용히 깨졌다.

- frozen은 **3~5문장**으로. "이걸 바꾸면 다른 게임이 된다" 수준만.
  - 예: *"경로 탐색 없음"*, *"색상 단독 신호 금지"*, *"서버 없음"*
- 나머지(수치, 구간 경계, 표현 방식)는 처음부터 **조정 가능** 영역으로 명시.
- 대신 **한 줄 규칙**을 세운다: `frozen을 건드리는 커밋은 decision-log에 한 줄을 추가한다.` 재협상 세션이 아니라 **한 줄**이면 08-13에도 지켜졌을 것이다.

### ⑥ 새 난이도 축을 넣을 때 "상호작용 표"를 의무화

조합 공간 검산표(풀 × 변장 ≥ 필요 쌍)는 훌륭했다. 같은 엄격함을 **축 간 결합**에도 적용한다.

새 축을 추가할 때마다 채워야 하는 표:

| 새 축 ↔ 기존 요소 | 결합 효과 | 의도한 것? |
|---|---|---|
| 순차 숨김 ↔ 오답 페널티(-3초) | 후반 오답 1회 = 타일 11장 즉시 숨김 | ❌ 미검토 |
| 순차 숨김 ↔ 시간 회복(+5초) | grace·간격 동시 3배 완화 | ❌ 미검토 |
| 순차 숨김 ↔ 미스매치 방패 | 시간 페널티 차단 = 숨김 전진도 차단 | ❌ 미검토 |
| 순차 숨김 ↔ 오답 재노출(08-13) | 방패와 결합 시 비용 0 전체 공개 | ❌ 미검토 |

**"시간을 건드리는 모든 것이 숨김 속도를 건드린다"** — 숨김 스케줄을 시간 비율로 정의한 순간 이 결합이 확정됐는데, 그 순간에 이 표가 없었다.

### ⑦ 순수 함수 테스트 한 파일은 스코프 예외로

7일 스코프에서 테스트를 뺀 판단 자체는 합리적이었다. 다만 **`balance.ts` 전체가 순수 함수**고, 여기서 실제로 버그가 두 번 났다(변장 몰림, 시간 회복 소실).

최소 세트 — 반나절이면 충분하다:
- 구간표 전 구간에서 `iconPool × disguiseCount ≥ pairCount` (조합 공간)
- 숨김 상한 70% / 하한 4장 / 단조성 (스펙 AD-6 세 규칙)
- `generateBoard`가 모든 (아이콘, 변장) 조합을 유일하게 생성
- **축 상호작용**: 오답 페널티 적용 후 숨김 수가 급증하지 않는지 (③에 해당)

`npx tsc -b`(`--noEmit`이 아니라)를 lint와 함께 스크립트에 넣는 것도 같은 범주다.

### ⑧ 컨셉 한 문장을 1일차에 고정하고, 브리프를 미결로 끝내지 않기

07-16 브리프가 **미결 질문에 답을 기다리다 중단**됐고, 그 상태가 첫 충돌을 만들었다. 브리프를 닫지 않고 넘어가면 다음 문서가 그 공백 위에 지어진다.

- 미결 질문이 남은 문서는 "미완결"로 명시하고, **다음 단계 문서가 그것을 첫 줄에서 확인**하게 한다.
- 게임 정체성 한 문장은 1일차에 쓰고, **바꾸려면 실기기 근거를 요구**한다. 그러면 #6(07-19 탁상 기각)이 애초에 일어나지 않는다.
