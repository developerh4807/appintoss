# Accessibility Review — 패턴매칭 두뇌자극 게임 (2026-07-19)

## Overall verdict

The photosensitivity mitigation for the new critical-state vignette/pulse is genuinely well-reasoned and quantified (edge-only coverage, ~0.83–1.67 Hz, both comfortably under the WCAG 2.3.1 3-flashes/second gate), and the icon-based match signaling remains colorblind-safe. But two concrete WCAG failures survive in this spec as written: a measurably wrong contrast claim that lands on the single most urgency-critical piece of text in the whole redesign, and a total absence of any WCAG 2.2.1 (Timing Adjustable) accommodation for users who structurally need more time — the ad-watch/retry-counter safety net only fires *after* failure, never during. Screen-reader access to the now-core countdown is deferred wholesale rather than decided, which is a UX call, not an implementation detail. This is not launch-ready from an accessibility standpoint until the contrast math is redone and a timing-adjustment story exists.

## Findings

- **critical** `error` (#FF6B5C) text on `surfaceBase`/board background (#FFF8EC) computes to ≈2.65:1 contrast — fails even the 3:1 *large-text* minimum, let alone 4.5:1 for normal text — yet this exact color/background pair is used for the two most time-critical readouts in the whole redesign: the enlarged critical-state timer digit and the "−3" mismatch penalty float. (`mockups/key-puzzle-main.html:81` `.timer-seconds.critical{color:#FF6B5C}`, `:137` `.penalty-float{color:#FF6B5C}`, against `.frame{background:#FFF8EC}` at `:35`). *Fix:* pick a darker/more saturated red reserved for text-on-cream use (verify ≥4.5:1), or stop coloring the text itself and instead pair a dark (`inkPrimary`) numeral with an `error`-colored icon/background chip — color the container, not the glyph.
- **critical** `DESIGN.md:81` states "`inkSecondary` on `surfaceBase` ≈ 4.6:1(WCAG AA 통과선)" — recomputing with the actual hex values (#8C8275 on #FFF8EC) gives ≈3.57:1, which fails WCAG AA for normal-size text (needs 4.5:1; only clears the 3:1 large-text bar). `inkSecondary` is used throughout at 12–15px — exactly *not* large text — for the stage label, retry-counter text ("무료 재시도 1/2회 사용함"), ad-slot placeholder, and hint copy (`mockups/key-puzzle-main.html:63,217`, `key-gacha.html:93,104`). *Fix:* re-verify with an actual contrast tool and either darken `inkSecondary` or restrict it to ≥18.7px/bold contexts; update the DESIGN.md claim to match reality either way.
- **critical** No mechanism satisfies WCAG 2.2.1 (Timing Adjustable) for users who structurally need more time (tremor/motor slowing taps, low vision needing longer visual scan, age-related processing speed). The only relief mechanisms — ad-watch-to-continue and a capped 2x free retry — both fire *after* a stage has already failed; neither lets a user complete the *same* timing challenge with more time. The stage 1–3 grace period is a one-time onboarding softener, not a standing accommodation. The one item that could help ("시간 회복," +5s) must be earned via currency from completing *other* timed stages fast — circular for exactly the users who need it. Given Commercial stakes and an explicitly 30–50대+/부모 세대 persona, this is a structural gap, not an edge case. (`EXPERIENCE.md` Accessibility Floor, lines 114–120, has no timing-adjustment bullet at all; `Component Patterns` "Retry counter" row, line 65; Key Flow 3a, lines 168–171.) *Fix:* add an explicit, currency-independent accommodation — e.g. a discoverable "여유 모드" that raises base stage time or disables the critical threshold — or make a deliberate, documented decision to invoke WCAG's essential-exception carve-out (timing is core to the JTBD) with legal sign-off, rather than leaving it unaddressed.
- **high** Screen-reader access to the countdown is entirely deferred (`[ASSUMPTION: 구현 단계에서 확정]`, `EXPERIENCE.md:119`) with no decision on announcement cadence, even though the timer is now the core loop. This isn't implementation trivia — "announce every tick" (SR-hostile spam) vs. "announce only at threshold entry" vs. "say nothing until failure" (SR users blindsided) are three different UX experiences and belong in this spec. Compounded by the timing gap above: without extended time, a screen-reader user cannot realistically complete a stage regardless of how the countdown is announced. *Fix:* specify at minimum a single `aria-live="assertive"` announcement at critical-threshold entry and at stage failure — not per-second updates — and cross-reference the Timing Adjustable gap so implementers don't treat this as solvable by ARIA alone.
- **medium** Internal contradiction between the stated Brand & Style baseline for this persona ("화면당 할 일은 하나," "여백은 넉넉하게," explicit rejection of "캔디크러시식 과포화 이펙트," `DESIGN.md:55`) and what the critical puzzle state now stacks on one screen simultaneously: thick pulsing/glowing timer bar + edge vignette pulse + enlarged red digit + "−3" floating text + tile flash, all animating together at the exact moment stress is highest (`EXPERIENCE.md:104`, "4가지가 동시에 켜진다"). This is functionally the oversaturated-effects pattern the doc explicitly rejects, just recomposed around the timer instead of match effects, and it reads as an unexamined collision rather than a deliberate tradeoff — the decision log documents *why* the timer got more urgent, but not why stacking four simultaneous animated cues is still consistent with "정돈된 귀여움" for this audience. *Fix:* either stagger the four critical-state cues' onset, drop one, or add an explicit rationale in DESIGN.md acknowledging and accepting this tradeoff.
- **medium** Bottom nav tab active state relies on color alone: `.tab.active { color: #0F6E6B }` vs. inactive `#8C8275`, same glyph, no fill/underline/weight change (`mockups/key-puzzle-main.html:165–174`). This is inconsistent with the project's own repeated "색상 단독 신호 금지" principle (explicitly applied to match tiles and to the timer's critical state) that simply wasn't extended to nav state. A colorblind or low-contrast-sensitivity user in the 30–50대+ demographic may not reliably tell which tab is active, especially since the two colors involved (`accent` teal, `inkSecondary` warm gray) are a hue-only distinction at small size (12px label, 20px icon). *Fix:* add a non-color cue for the active tab — a filled pill behind it (consistent with how the segment control already signals active state) or a bold-weight/filled-vs-outline icon swap.
- **low** The "0.6s 주기" phrasing used across `DESIGN.md:41,113`, `EXPERIENCE.md:104,117`, and the mockup CSS (`vignette-pulse 0.6s ease-in-out infinite alternate`) is ambiguous between "0.6s per half-cycle" (what the CSS actually implements — full cycle ≈1.2s, ≈0.83 Hz) and "0.6s full flash cycle" (≈1.67 Hz). Both readings stay safely under the WCAG 3 Hz gate, so this isn't a live violation today, but the spec never states the actual full-cycle frequency in Hz — only "분당 100회 미만" — so a future implementer tweaking the easing/direction could tighten the margin without realizing how close "0.6초" already sits to ambiguous territory. *Fix:* state the full-cycle frequency explicitly (e.g. "≈0.83 Hz full cycle, well under the 3 Hz/180-per-minute threshold") so the safety margin travels with the spec instead of being re-derived by whoever implements it.

## What holds up

The photosensitivity mitigation for the critical-state vignette is the strongest part of this review: edge-only coverage (not full-screen), a quantified sub-3Hz pulse rate, and an explicit rejection of full-screen red flashing are all present and correctly reasoned against WCAG 2.3.1's actual frequency gate — this wasn't hand-waved. Match determination is consistently icon-shape-based rather than color-based across every surface, which is genuinely colorblind-safe. The Reduce Motion fallback is well-designed: it preserves the emotional reveal climax while stripping motion, and correctly converts the timer's critical-state pulse into a static color+size cue rather than dropping the signal entirely — multi-channel signaling (color + motion + size + text) is real, not just claimed, for both the timer critical state and the mismatch penalty feedback. Tap targets (48px+) and the 16px body-text floor are appropriately generous for the stated persona, and the single-modal-dialog-stacking rule is followed consistently across all three mockups.
